# 통합 API 게이트웨이 프로토타입

외부 플랫폼의 API 키를 중앙 서버 한 곳에서 관리하고, 직원에게는 개인별 내부 키를 발급하는 구조를 시연하는 프로토타입입니다.
외부 플랫폼은 가상 서버로 구현되어 있어 실제 키나 비용 없이 실행할 수 있습니다.

```
직원 (내부 키) ──▶ 통합 API 게이트웨이 :8000 ──▶ 가상 외부 플랫폼 :9000
                   인증 · 개인 한도 · 예산         AI 요약 / 거래처 조회 / 번역 / 환율 / OCR
                   캐시 · 요청 병합 · 대기열        (계정 키마다 요청 한도, 과금)
                   재시도 · 서킷 브레이커 · 기록
```

## 실행

Python 3.11 이상이 필요합니다.

```bash
pip install -r requirements.txt
```

```bash
python run.py
```

실행 후 브라우저에서 엽니다.

| 주소 | 내용 |
|---|---|
| http://localhost:8000 | **소개 페이지** (IT를 잘 모르는 직원용, 첫 화면) |
| http://localhost:8000/dashboard | 트래픽 시뮬레이션 대시보드 |
| http://localhost:8000/docs | 게이트웨이 API 문서 (직접 호출해 볼 수 있음) |
| http://localhost:9000/docs | 가상 플랫폼 API 문서 |

## 다른 사람에게 공개하기

### 같은 사무실 네트워크

```bash
python run.py --host 0.0.0.0
```

다른 PC에서 `http://<이 PC의 IP>:8000` 으로 접속합니다. IP는 `ipconfig` 의 IPv4 주소입니다.
Windows 방화벽 창이 뜨면 **개인 네트워크**만 허용하세요. 이 방식은 9000번(가상 플랫폼)도 함께 열립니다.

### 외부 인터넷 (Cloudflare Quick Tunnel)

계정 없이 임시 HTTPS 주소를 받아 8000번만 외부에 공개합니다. 공유기 포트포워딩은 필요 없습니다.

1. cloudflared 설치 (처음 한 번)

   ```bash
   winget install --id Cloudflare.cloudflared
   ```

2. 서버 실행 (`--host` 옵션 없이 평소대로)

   ```bash
   python run.py
   ```

3. 다른 터미널에서 터널 열기

   ```bash
   cloudflared tunnel --url http://localhost:8000
   ```

4. 출력된 `https://xxxx.trycloudflare.com` 주소를 공유합니다. 대시보드는 주소 뒤에 `/dashboard` 를 붙입니다.

- 터널 창을 닫으면 공개가 끝나고, 다시 열 때마다 주소가 바뀝니다.
- 이 PC가 꺼지거나 절전 모드에 들어가면 접속이 끊깁니다.
- 게이트웨이는 가상 플랫폼을 `127.0.0.1:9000` 으로 부르므로 9000번은 외부에 열 필요가 없습니다.

**공개 전 확인**

- `config.yaml` 의 `admin_key` 를 추측하기 어려운 값으로 바꾸세요. 바꾼 뒤 `run.py` 를 다시 실행해야 반영됩니다.
- 시연 편의를 위해 소개 페이지와 대시보드 HTML에 관리자 키가 그대로 들어갑니다. 주소를 아는 사람은 직원 키 조회·발급·폐기, 초기화, 시나리오 실행을 할 수 있으므로 주소는 필요한 사람에게만 공유하세요.
- 시연이 끝나면 터널을 닫고, 필요하면 대시보드의 **초기화** 버튼으로 기록을 비웁니다.

## 시연 방법

### 1부: 소개 페이지 (게이트웨이가 왜 필요하고 어떻게 동작하는지)

IT를 잘 모르는 직원에게 설명할 때는 소개 페이지(`/`)로 시작합니다.

1. **왜 필요한가요?**: 지금 방식(회사 키를 나눠 씀)과 게이트웨이 방식을 그림으로 비교합니다. "법인카드를 나눠주는 대신 구매 담당자에게 요청한다"는 비유로 설명합니다.
2. **직접 해보기**: 직원과 업무를 고르고 **요청 보내기**를 누르면 `직원 → 게이트웨이 → 외부 서비스 → 게이트웨이 → 직원` 흐름이 5단계로 천천히 표시되고, 결과가 알아보기 쉬운 카드로 나옵니다. 실제 서버 통신 결과입니다.
   - **같은 요청을 한 번 더** 보내면: 외부 서비스에 다시 묻지 않고 저장된 결과를 쓰는 모습(비용 0원)을 보여줄 수 있습니다.
   - **퇴사 처리해 보기**를 누른 뒤 요청하면: 게이트웨이가 그 직원의 요청만 막는 모습을 보여줄 수 있습니다. 다시 누르면 복구됩니다.
   - **개발자용: 실제로 오간 요청과 응답 보기**를 펼치면: 직원의 사원 키가 게이트웨이에서 회사 키로 바뀌어 나가는 실제 요청을 보여줍니다.
3. **관리자 기록**: 방금 보낸 요청이 누구 이름으로, 얼마의 비용으로 기록됐는지 보여줍니다.

### 2부: 트래픽 시뮬레이션 (여러 명이 동시에 쓰면?)

대시보드(`/dashboard`)에서 시나리오 버튼을 누르면 **같은 요청 계획을 두 방식으로 동시에 실행**합니다.

- **게이트웨이 없음**: 직원들이 공유 키 하나로 플랫폼을 직접 호출
- **게이트웨이 경유**: 직원마다 내부 키로 게이트웨이를 호출

두 방식은 가상 플랫폼에서 서로 다른 계정으로 처리되므로 한도를 따로 씁니다. 공정한 비교를 위해서입니다.
시나리오를 시작할 때마다 한도와 서킷 상태는 초기화되고, 캐시는 유지됩니다.

| # | 시나리오 | 보여주는 기능 | 검증 결과 예시 (직접 → 게이트웨이) |
|---|---|---|---|
| 1 | 출근 시간 몰림 | 속도 제한, 대기열 | 성공률 17% → 100% |
| 2 | 같은 요청 반복 | 캐시, 요청 병합 | 플랫폼 호출 60회 → 2회, 청구액 1,311원 → 44원 |
| 3 | AI 요약 폭주 | 동시 실행 제한 | 성공률 30% → 100% |
| 4 | 과다 사용자 | 사용자별 한도 | 다른 직원 성공 2/30 → 30/30 |
| 5 | 플랫폼 장애 | 재시도, 서킷 브레이커 | 불안정 구간 성공률 약 65% → 100% |
| 6 | 퇴사자 키 폐기 | 키 관리 | 퇴사자 호출 성공 2/2 → 0/2 (차단) |
| 7 | 평상시 업무 (종합) | 전체 | 성공률 60% → 100%, 플랫폼 호출 380회 → 232회 |

숫자는 무작위 요소가 있어 실행할 때마다 조금씩 달라집니다.

**발표 팁**
- 각 시나리오 설명 아래의 "주목할 점"을 따라 설명하면 됩니다.
- 청구액은 게이트웨이 쪽이 더 클 수 있습니다(AI, 종합 시나리오). 거절 없이 실제로 처리한 유료 요청이 더 많기 때문입니다. 중복 호출을 막아 아낀 금액은 **캐시로 아낀 비용**에 따로 표시됩니다.
- 시연 전에 **초기화** 버튼을 누르면 사용량, 캐시, 한도 상태가 모두 비워집니다.

터미널에서도 실행할 수 있습니다(서버가 켜져 있어야 합니다).

```bash
python -m simulator.load_test rush
```

## 직원용 API 사용 예

키는 관리자 API로 발급하거나, 시드된 직원 키를 조회해서 씁니다.

```bash
curl -X POST http://localhost:8000/admin/keys -H "X-Admin-Key: <config.yaml 의 admin_key>" -H "Content-Type: application/json" -d "{\"name\": \"홍길동\", \"dept\": \"영업1팀\"}"
```

```bash
curl "http://localhost:8000/v1/biz/status?b_no=1234567890" -H "X-API-Key: <발급받은 키>"
```

PowerShell 5.1에서는 `curl` 대신 `curl.exe` 를 쓰세요. `/docs` 화면에서 호출해 보는 방법이 가장 쉽습니다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/v1/ai/summarize` | 문서 요약 `{"text": "..."}` |
| GET | `/v1/biz/status?b_no=` | 사업자 상태 조회 |
| POST | `/v1/translate` | 번역 `{"text": "...", "target_lang": "EN"}` |
| GET | `/v1/fx/rates?currency=USD` | 환율 조회 |
| POST | `/v1/ocr` | 영수증 인식 `{"filename": "..."}` |
| GET | `/v1/me/usage` | 내 사용량과 남은 예산 |

모든 응답의 `meta` 에 처리 경로가 담깁니다.

```json
"meta": { "platform": "biz", "source": "cache", "queued_ms": 0, "retries": 0, "cost_krw": 0, "latency_ms": 1 }
```

`source` 는 `origin`(플랫폼 호출), `cache`(캐시), `coalesced`(동시 요청 병합) 중 하나입니다.
비용과 대기 시간은 실제로 플랫폼을 호출한 `origin` 요청에만 매깁니다.

**처리 순서**

게이트웨이는 요청을 아래 순서로 검사하고, 막히는 단계의 에러 코드로 응답합니다. 성공과 실패 모두 사용량 기록에 남습니다.

| 단계 | 모듈 | 막히면 |
|---|---|---|
| 1. 인증 | `auth.py` | 401 `INVALID_KEY`, `KEY_REVOKED` |
| 2. 개인 한도 (분당 요청, 동시 요청) | `limiter.py` | 429 `USER_RATE_LIMIT`, `USER_CONCURRENCY_LIMIT` |
| 3. 일일 예산 (유료 플랫폼만) | `usage.py` | 429 `BUDGET_EXCEEDED` |
| 4. 캐시, 요청 병합 | `cache.py` | 적중하면 플랫폼 호출 없이 바로 응답 (비용 0원) |
| 5. 서킷 브레이커 | `resilience.py` | 503 `CIRCUIT_OPEN` |
| 6. 플랫폼 대기열 | `limiter.py` | 503 `QUEUE_FULL`, `QUEUE_TIMEOUT` |
| 7. 플랫폼 호출 (회사 키로 교체) | `proxy.py` | 5xx·429면 백오프 후 5단계부터 재시도, 끝내 실패하면 502/504 |
| 8. 사용량 기록 | `usage.py` | |

**에러 코드**

| HTTP | 코드 | 의미 |
|---|---|---|
| 401 | `INVALID_KEY`, `KEY_REVOKED` | 잘못되었거나 폐기된 키 |
| 429 | `USER_RATE_LIMIT`, `USER_CONCURRENCY_LIMIT`, `BUDGET_EXCEEDED` | 개인 한도·예산 초과 |
| 503 | `QUEUE_FULL`, `QUEUE_TIMEOUT` | 대기열이 가득 찼거나 너무 오래 기다림 |
| 503 | `CIRCUIT_OPEN` | 플랫폼 장애로 호출을 일시 중단 |
| 503 | `PLATFORM_QUOTA_EXHAUSTED` | 플랫폼의 일일 한도 소진 |
| 502/504 | `PLATFORM_ERROR`, `PLATFORM_TIMEOUT` | 재시도 후에도 플랫폼 오류 |

## 설정

`config.yaml` 에서 코드 수정 없이 바꿀 수 있습니다. 바꾼 뒤 `run.py` 를 다시 실행하세요.

- 플랫폼별 한도(`platform_limit`), 게이트웨이 한도(`gateway_limit`), 단가, 응답 속도, 오류율, 캐시 시간
- 직원 수, 개인 분당 한도, 동시 요청 수, 일일 예산
- 재시도 횟수와 간격, 서킷 브레이커 기준

게이트웨이 한도는 플랫폼 한도보다 여유 있게 잡습니다. 게이트웨이가 보낸 시각과 플랫폼이 받은 시각 사이에 지연이 있어서, 한도를 똑같이 맞추면 플랫폼 쪽에서 초과로 판정될 수 있기 때문입니다.

## 구조

```
api_gateway/
├── run.py                 # 두 서버를 한 번에 실행
├── config.yaml            # 모든 수치 설정
├── common/                # 설정 로더, 플랫폼 정의·과금 계산, 샘플 텍스트
├── mock_platforms/        # 가상 외부 플랫폼 (한도, 지연, 장애, 청구 집계)
├── gateway/
│   ├── app.py             # 직원용 API, 처리 흐름
│   ├── auth.py            # 직원·내부 키 관리 (SQLite)
│   ├── limiter.py         # 플랫폼 대기열, 사용자별 한도
│   ├── cache.py           # 캐시, 요청 병합
│   ├── resilience.py      # 서킷 브레이커
│   ├── proxy.py           # 플랫폼 호출, 재시도
│   ├── usage.py           # 사용량·비용 기록
│   └── admin.py           # 관리자 API, 대시보드 데이터
├── simulator/             # 시연 시나리오, 실행기, CLI
├── dashboard/
│   ├── intro.html         # 소개 페이지 (왜 필요한지, 요청 흐름 체험)
│   └── index.html         # 트래픽 시뮬레이션 대시보드
└── data/                  # 실행 시 생성되는 SQLite DB
```

## 프로토타입의 한계 (실서비스 전환 시 추가할 것)

- 원본 플랫폼 키를 설정 파일 대신 Secret Manager·Vault에 보관
- 캐시와 한도 카운터를 메모리 대신 Redis로 옮겨 서버 여러 대로 이중화
- HTTPS, 관리자 로그인 (지금은 대시보드에 관리자 키가 그대로 들어 있음)
- 사내 SSO 연동으로 키 자동 발급·회수
- 실제 플랫폼 연동: 플랫폼마다 인증 방식과 요청·응답 형식이 다르므로 `gateway/proxy.py` 에 플랫폼별 변환(어댑터)을 추가하고, `common/platforms.py` 의 과금 규칙을 실제 요금표에 맞춤
